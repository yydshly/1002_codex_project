[项目介绍](../README.md) · [源码研究](research.md) · [工作台](../web/index.html) · [网页产品探索](../web/research.html#exploration)

## 当前产品主线：从用户的图或粗模，生成一致的完整场景

2026-10-05 明确的目标是：用户画出场景，或检查由这张图得到的粗模；控制模型以它为依据，组织生成与修正，得到可从不同角度观察、可继续编辑的完整 3D 场景。用户提交的是一个场景意图，最终验收的是同一个场景。下文的固定海岛编辑器、材质预览与单对象生成记录，是已有实验，不代表这条主线已经实现。

图和粗模是同一份创作意图的两种表达，不要求用户重复输入。俯视布局表达区域、位置和连接；透视画或照片中的空间需要先解释并检查，不能直接把图片坐标当作地面坐标。粗模可以把这些空间决定明确下来。额外的外观参考、文字、资源和规则用于补充要求，不是必填的第二张图，也不替代用户的场景输入。

目标流程是：**我的图 / 对应粗模 → 模型理解空间与外观要求 → 生成完整 3D 候选 → 对照原输入检查并修正 → 确认保存**。内部可以分阶段生成、调用资产服务或编写场景代码；对用户呈现的仍然是一项完整场景任务，无需逐个生成和装配所有物体。

这里的“一致性”要检查三个方面：

- **忠于空间意图：** 岸线、道路、关键对象的位置、数量、尺度和关系符合用户确认的图或粗模。细节补全可以丰富外观，空间调整应明确展示并让用户决定。
- **形成统一的场景：** 建筑、地形、植被、水面在尺度、材质、光照和接触关系上协调；多角度观察时仍然成立。写实程度是质量目标，需要验收，不能由三角形数量或生成成功推断。
- **延续已确认的决定：** 修改指定区域时，保留其他已确认内容；候选能比较、拒绝和恢复。草图没有表达的背面、内部和细节允许补全，再由用户检查。

**已推进的第 08 步：** 在当前页面保留第 05–07 步呈现，新增真实控制模型任务。它读取完整 plan、绘笔布局图、粗模正反斜视，以及存在时的原始参考图；返回覆盖全部原 ID 的整场景方案。执行器据此选择七类对象／区域的形态处理、材质配色、密度、受保护微地形和整体光照，组合既有素材、已生成神经资产与程序几何。首轮已通过本机 Codex CLI 的真实模型调用，源布局指纹为 `plan-v1-162afc9e3f46f3aa-22227`，25 个原对象完整保留。模型身份显示实际 provider 与 CLI 版本；未报告具体模型 ID 时不推测，也不称为 Opus。

**一致性如何执行：** 输出没有坐标和外部资源 URL，直接使用原始布局生成空间，禁止增删或改名原对象。局部修改将原环境和范围外记录约束为上一方案的原值，服务端再逐字段校验；越界候选拒绝应用。原草案、现有第 05–07 步效果与新模型候选分开保存。用户可以同视角切换粗模、检查另一侧、确认保存、回退上一候选，并导出含实际输入图片、原 plan、模型回执、配方与执行来源的 JSON。

**仍有的缺口：** 当前控制模型输出的是受已注册场景工具支持的完整方案，不是任意精细网格或任意世界的自由创建。第 06 步的神经模型仍只读取单个物体图片；第 08 步并未让它们直接理解整片粗模。空间与修改范围有程序检查；写实品质、背面、接触关系及跨视角外观仍需用户验收，没有自动视觉评分或自主修复闭环。“对标最终效果”是生成与验收目标，不是已经实现的品质承诺。

## 已有实验记录

第一版产品是“在现成海岛中编辑一个作品”的浏览器工作台。用户面对实时 3D 画面、对象、属性和修改记录，交付的是可再次打开的配置与画面。原生工作台已经实现；真实 Opus 接入、云端发布和模型自动生成精细新世界尚未实现。

参考图片与语义绘笔两个本地实验入口覆盖人工标注、布局、结构化 plan、真实 3D 粗模、基础局部编辑与本地备份。现在增加选中陆地的本地细化：先预览沙滩、岩石和植被候选，再比较、应用或取消。它与原生固定海岛编辑器分开：原工作台控制六个注册对象和环境；新实验根据用户定义的布局构建程序几何。精细世界、完整空间关系、玩法和云交付仍是后续设计，不能把本地细化等同于模型自动复原图片或完整 Tidewater 世界生成。

## 给谁用，解决什么问题

首个假设用户是制作海岛主题交互展示、活动页面、场景概念或虚拟构图的设计师与开发者。他们希望持续调整同一个作品：保留满意的布局，只修改一个小屋、一个镜头或海况，并能找回旧状态。

本次实现验证编辑闭环，尚没有证明这些用户愿意付费。后续可以先以“海岛主题交互场景模板 + 编辑器”验证需求：用户从模板进入，在受约束的资产内编辑、预览、保存，最终发布或嵌入一页交互场景。模板品质、稳定编辑与交付能力可以构成收费对象；调用一次模型本身不构成完整产品。

原工作台交付本地编辑器、配置 JSON 和 PNG；新增实验交付可继续编辑的 plan JSON（包含缩小后的参考图）和生成说明文本。不包含发布服务、账号、云协作、GLB 或通用工程。两个 JSON 格式分别依赖各自执行器，不能互相导入或当作通用 3D 格式直接交给其他引擎。

## 一次完整使用流程

以“把小屋移到旁边，做一张日落海岛画面”为例：

1. 打开工作台，等待真实 Tidewater 渲染器就绪。界面清楚显示本地指令模式。
2. 从对象列表或 3D 视图点选“工作台小屋 A”；属性面板显示这个具体对象。
3. 输入“把选中的物体向右移动10米”。本地解析得到 `cabin-a.x = -25`，画面和属性同时更新。“右”使用世界 X 轴正方向，不随镜头改变。
4. 输入“改成日落，海浪平静一点”。只改时间和涌浪，布局保持；整条指令进入一次历史。
5. 对比效果，撤销或重做；满意后锁定小屋，再改灯塔或另一座小屋。
6. 独立切换鸟瞰、码头、船边镜头，导出原生 GPU 画面 PNG。
7. 保存到当前浏览器，另导出 JSON 作为备份。重新导入可以恢复这些编辑参数。

用户不需要读懂 WGSL；他仍然可以准确控制对象与参数。文字是一种输入方式，面板、选择和历史共同构成产品。

## 产品如何控制场景

```text
属性面板 / 预设 / 本地指令 / 未来模型动作
                       ↓
           对象 ID、参数范围、锁定校验
                       ↓
            整组操作形成一次状态事务
                       ↓
         场景 JSON / 撤销重做 / 本地保存
                       ↓
               同源 iframe 适配器
                       ↓
      原生 Tidewater 对象、FFT 海水、天空与镜头
```

状态模块 `scene-core.js` 与渲染器分离。它只接受有限字段、已注册对象 ID、有限数值和参数范围；一组动作先在副本上验证，再替换场景。失败不会留下半个修改。界面变化不等于 GPU 成功，因此运行时另外报告初始化、进度和错误。

对象用稳定 ID 寻址，避免“遍历第 17 个 mesh”随实现变动。渔船还要同步船控制器：仅修改可见 group 会被下一帧物理更新覆盖。编辑模式固定船姿态，进入漫游恢复游戏行为。

实际动作结构如下，直接适配本地执行器：

```json
[
  { "type": "object", "id": "cabin-a", "values": { "x": -25, "rotation": 20 } },
  { "type": "environment", "values": { "timeOfDay": 18.3, "swell": 0.264 } },
  { "type": "camera", "preset": "overview" }
]
```

`object` 可改 `x/z/rotation/scale/visible/locked`；`environment` 可改 `timeOfDay/windSpeed/swell/cloudCover`；`camera` 与 `preset` 各接受已登记预设。锁定对象只能修改 `locked`，需先解锁才能变换。导入检查版本、完整字段和 64 KB 文件上限；无效文件不覆盖当前配置。

## 和直接让模型生成代码有什么区别

| 用户要做的事 | 直接让模型重新生成代码 | 本工作台 / 后续模型动作 |
| --- | --- | --- |
| 只移动小屋 A | 模型需要定位源码并改写实现 | `object` 动作准确指向 `cabin-a` |
| 改日落但保留布局 | 依赖提示和代码修改范围 | 环境与对象是分开的状态字段 |
| 回到上一版 | 要保存、比对或恢复代码版本 | 一个动作事务可以一次撤销 |
| 留下可交付作品 | 代码还需运行、打包和管理资源 | 当前可保存 JSON/PNG；发布服务待建 |
| 输入无法实现的效果 | 可能继续生成未验证代码 | 校验拒绝未知字段和缺失模块 |

直接写代码仍适合扩展新能力，例如实现雨、载入新模型、增加时间轴；运行中的用户编辑则通过稳定动作接口。两层可以同时使用。工作台的价值在于固定世界与可控修改、恢复和交付，而不是替用户多写一句提示词。

## 模型自由生成的控制边界

如果把描述或图片交给模型，让它任意重写整个场景实现，产品主要能提供方向、预览和重试。提示词不能保证已有建筑保持原样、道路始终可达，或背面空间合理。图片能让目标更明确，但不会自动建立这些保证。

允许模型创造新物体、新地形或程序化效果，与控制作品并不冲突。前提是生成结果接入场景结构：对象具有稳定 ID、资源与版本引用、位置和关系；修改有明确范围；已确认部分可以锁定；操作能校验、比较和恢复。新能力的代码开发与运行中编辑应分别管理，不能把任意模型代码直接当作现有动作执行器的输入。

| 希望控制的内容 | 产品需要保存和执行什么 | 仍需验收的部分 |
| --- | --- | --- |
| 灯塔位置、数量、尺寸 | 坐标、单位、对象 ID、数值约束 | 模型外形与材质是否合意 |
| 保留已确认建筑 | 对象及资源版本、锁定范围、修改差异 | 新增内容是否遮挡原构图 |
| 港口靠水、道路连接村庄 | 空间关系与生成规则，地形与路径检查 | 碰撞、导航和实际步行测试 |
| 在指定时刻触发事件 | 事件、状态与时间轴 | 动画表现与触发条件是否符合任务 |
| 从某个角度接近参考图 | 相机、参考区域与外观要求 | 构图、造型、光照需视觉对照，不能保证像素级复原 |

原工作台实现有限动作的字段、范围、对象 ID 和锁定检查；新实验增加 plan 的严格结构、坐标、点数、高度和基础几何检查。它们都没有实现道路可达、碰撞、导航或任务校验。会话历史与本地 JSON 也不是完整工程和生成资源的版本系统。

## 两个本地实验入口

[参考图片](../web/create.html?entry=image) 与 [语义绘笔](../web/create.html?entry=layout) 共享同一独立草案。入口决定初始视图，不会创建两份不同作品或清空已有标注。原生 [海岛工作台](../web/index.html) 保留原能力。

| 已实现实验能力 | 实际行为与边界 |
| --- | --- |
| 图片参考 | 上传 PNG/JPEG/WebP，缩小并转换为 JPEG 预览后嵌入 plan；也可使用已有海岛截图。人工标注，不识别物体、深度或尺度 |
| 外观要求 | `intent` 保存用户文字，进入本地生成说明；未发送给模型，未按文字自动改场景 |
| 语义绘笔 | 陆地/水域自由轮廓闭合为多边形，道路形成路径，小屋/灯塔/棕榈/船形成单点标记 |
| 空白与示例 | 新建为空白，默认底海只是预览背景；用户显式载入“两岛示例”，不冒充自动创作 |
| 场景 plan | 稳定实体 ID、区域/路径/标记、归一化点、高度、锁定、世界尺寸、风格与参考图；基础字段和数值校验 |
| 局部编辑 | 画布/列表/粗模选中同一 ID，画布拖动或输入中心 X/Z、高度；锁定保护位置、形状、高度与删除；可只清除未锁定对象 |
| 历史 | 30 步会话撤销/重做；不随刷新恢复 |
| 真实粗模 | 点击生成后，独立预览使用 Tidewater Engine/几何/数学与轻量 WGSL 构建真实几何；旋转、缩放、俯视/斜视和选择；默认后续自动更新，可关闭 |
| 选中陆地细化 | 热带海岸、岩岸草甸或花园岛方向，密度和沙滩/岩石/植被开关；临时候选与修改前比较，应用后入历史并保存；本地规则，不调用模型 |
| 本地保存 | 独立 IndexedDB 自动或显式保存，完整 plan JSON 导入导出；JSON 保留缩小后的参考图像素 |
| 生成说明 | 由 plan 组织布局、坐标、文字意图和锁定要求，可以复制或下载；不含图片像素，不调用 Opus/API |

图片上的标注与俯视布局共用画布 0..1 坐标。照片中的投影位置不是物体在地面上的真实坐标；用户需要切换到俯视布局，校正距离、位置与空间关系。粗模使用用户定义的世界尺寸，默认 200 × 150 米，不从参考图测量真实尺度。

当前可创建不同的手动布局与对应粗模，再对选中陆地增加程序细节，但没有图片自动分割、深度恢复、生图、高精度 image→3D、精细资源自动生成、任意资产导入、碰撞/导航或玩法。新预览不载入原海岛的完整 FFT 海水、大气/云和游戏物理管线，也不会修改原岛地形。

### 粗模之后的实际产品步骤

用户已经用绘笔确定岛屿、水面、道路与关键对象，下一步应让他在保留这些决定的基础上逐块补充内容。新增“细化选中区域”卡片把这个流程变为实际操作；本轮只支持陆地，不自动细化建筑或生成任意资产。

1. **确定范围。** 从卡片下拉框、画布、列表或 3D 选择同一块陆地。锁定目标不能生成、替换或移除细化，需要先解锁。
2. **确定方向。** 选择热带海岸、岩岸草甸或花园岛；密度为稀疏、适中或丰富。沙滩、岩石与植被分别开关。外观说明文本和参考图仍作为人工参考，不会被本地生成器自动理解。
3. **查看候选。** 点击“预览细化”，当前草案的副本产生候选；可以“换一版”，也可以切换“修改前/候选效果”查看同一布局。预览不保存，也不会立即覆盖已有细化。
4. **明确接受。** “应用细化”把候选一次提交到历史和草案；“取消”恢复已有结果。其他草案修改或切换目标会取消候选，避免把过期候选应用到不同方案。
5. **继续编辑和恢复。** 已应用细化可移除、撤销或重做，随本地草案保存及 JSON 导出/导入。移动陆地或调整轮廓后，细节由当前规则重建；会话历史仍不是完整工程版本系统。

细化记录在陆地实体上，派生显示几何不另行改写原陆地边界、高度、水域、道路、建筑或标记，也不将装饰冒充可编辑建筑资产。沙滩属于表面几何，岩石与植被属于程序装饰；生成与避让只负责本轮显示布局，不证明地形、碰撞、路线或生态物理有效。

[纯函数生成器](../web/creation-refinement.js) 按米制尺度检查装饰落点及占地，避开水域、道路、已有物体标记和被更高陆地覆盖的区域，并保留边界间隔。密度控制预算与间距；小区域、凹形或障碍较多时，可用空间不足会减少实际装饰，不通过强行塞满来满足固定数量。沙滩由预览器派生为表面几何，仍不改变方案边界。

本轮 plan 最多允许 5 块陆地带有细化配置，每块最多 48 个装饰，全场景最多 240 个。预算固定归属单块陆地，新增或移除另一块的细化不会改变已有区域的装饰分配，因此不会因其他区域抢预算而改变锁定陆地的细节。达到上限后仍可替换已细化区域的配方；要细化新的区域，需先移除另一块的配置。这个限制也在导入与事务校验中执行。

当前实际结构为陆地实体的可选字段：

```json
"refinement": {
  "preset": "tropical",
  "seed": 42,
  "density": 2,
  "beach": true,
  "rocks": true,
  "vegetation": true
}
```

`preset` 限定为 `tropical/rocky/garden`，`seed` 是无符号 32 位整数，`density` 为 1、2 或 3，三个开关必须为布尔值。原来没有 `refinement` 的 plan 仍能载入并显示粗模；存档保留参数，显示几何由生成器重建。

这个流程的价值是把“这次允许增加什么、在哪块陆地增加、是否接受”保存为明确操作。未来模型可以输出同类结构化修改，并经过相同 ID、字段、锁定与预算校验再预览；它不能直接绕过这些检查。模型 API、参考图理解和生成资源管理还没有接入。

### plan 与原工作台协议分开

以下是新实验的有效最小示例，区别于只记录六个对象的原生工作台存档。它描述用户定义的粗模方案，不是 Tidewater 原生 API：

```json
{
  "version": 1,
  "name": "灯塔布局",
  "entry": "layout",
  "intent": "保留灯塔位置，后续增加周围陆地。",
  "world": { "width": 200, "depth": 150 },
  "style": { "lighting": "day", "waterColor": "#3b8d9c", "landColor": "#6c956b" },
  "reference": null,
  "entities": [
    { "id": "lighthouse-main", "kind": "lighthouse", "points": [{ "x": 0.5, "y": 0.4 }], "height": 18, "locked": true }
  ]
}
```

实体限定为 `land/water/road/cabin/lighthouse/palm/boat`。陆地和水域至少三点，道路至少两点，物体标记恰好一点；最多 120 个实体、每实体 256 点、总计 4096 点。高度范围 0..100 米；world 宽/深支持 10..2000 米，当前页面显示尺寸，导入可提供有效尺寸。仅陆地支持上述可选 `refinement` 字段。plan 严格拒绝未知字段、重复 ID 和非有限数值。单次操作在副本上验证后提交，不允许锁定对象被更新或删除；解锁是独立动作。

参考图存储的是经过缩小的图像，不是原始文件。生成说明中“最近陆地”按中心距离计算，不等于对象位于陆地内或道路可达。当前基础 schema 不提供完整空间关系、模型代码执行或物理有效性保证。

### 存储与旧版保留

新草案使用 IndexedDB `tidewater-creation-lab.v1` 的 `drafts/current`，不覆盖原工作台 `tidewater-studio.v1`。启动时只在备份键不存在时复制原配置到 `tidewater-studio.before-creation-inputs`。草案随当前浏览器和 origin 保存；完整 JSON 是另行备份，生成说明文本不代替 plan。

本次新增前的 [旧工作台](../web/previous/index.html) 和 [旧研究页](../web/previous/research.html) 继续可访问，共用未改动的 runtime。旧源、文档和截图另保存在 `versions/2026-10-04-before-creation-inputs/`，见 [14 文件 SHA-256 清单](../versions/2026-10-04-before-creation-inputs/manifest.json)。它保存网页版本与关键源文件，并未复制另一份完整原生素材包。

## 语义布局到可交付场景

完整产品以“画出世界的结构，再逐步生成和确认”为主流程。当前实验已实现布局、基础 plan、真实粗模、选中陆地的程序细化、局部编辑与本地备份；概念图与精细 3D 自动生成、完整关系规则和玩法仍是规划。图片可以补充风格与外观；语义布局、空间关系、已有资产和规则共同提供 3D 依据。

```text
目的与文字描述 / 语义绘笔布局 / 参考图 / 现有资产 / 空间数据
                              ↓
                  结构化场景方案，确认布局与关系
                              ↓
          概念图确认外观 → 3D 粗模确认空间与新视角
                              ↓
                  精细 3D、材质、环境与动画
                              ↓
              局部编辑 / 按需增加玩法或镜头时间轴
                              ↓
                    保存版本与交付真实场景
```

1. **画语义布局。** 基础绘笔已实现水面、陆地、道路与四种物体标记。完整方案还需建筑/植被区、港口等更多语义，表达“这里是什么、彼此怎样连接”，不要求用户画出精细美术。
2. **确认结构化方案。** 当前已能查看实体、移动位置、修改高度并锁定，基础 plan 保存尺度、外观要求和参考图。后续要增加明确空间关系、资产需求、生成范围与分阶段确认。仅把草图作为视觉提示交给模型，仍无法保证结果服从布局。
3. **用概念图确认外观。** 概念图帮助选择风格、主体造型、色彩与光照，标记满意区域。它是可选的视觉确认环节，不证明空间完整，也不替代场景结构。当前没有接入概念图生成接口。
4. **用真实 3D 粗模确认空间。** 当前已能把手动布局创建为陆地、水面、道路和简化物体，从不同视角观察尺度和遮挡。参考相机对齐、步行/航行路线与物理可达检查仍待建设。图片中看不到的部分需要明确补全；构图确认与空间确认分别进行。
5. **按确认范围生成精细内容。** 当前先提供选中陆地的程序细化，保留边界并增加沙滩、岩石与植被，候选比较后再接受。后续在保留对象 ID 和空间关系的前提下，替换体块为详细资源，细化材质、天空、海水和动画。模型可以创作新内容；产品记录替换了什么、使用哪些资源、能否回退。地形变化还需同步岸浪、碰撞、导航和其他依赖模块。
6. **局部编辑与可选行为。** 当前可通过画布和属性做局部修改、锁定与撤销，模型变更尚未接入。后续让模型按明确范围提出修改，执行层保护锁定内容并检查约束。游戏用户设置触发器、任务与交互，视觉用户设置镜头和时间轴，无需所有用户都进入同一套复杂流程。
7. **交付和版本。** 当前已有本地 plan/参考图保存和 JSON，原工作台另有配置 JSON 和 PNG；会话撤销不等于完整版本。目标还需保存资源引用、生成结果和修订，提供发布、资源打包、通用工程导出与完整恢复。

当前新 plan 已单独记录区域/对象 ID、边界或坐标、世界尺寸、外观、参考图和实体锁定，不套用六对象存档。下一阶段需要连接和邻接关系、资产引用、参考相机、生成范围与持久修订，再由生成模块和对应适配器处理。轻量预览能接受该 plan，不代表完整海洋、村落与游戏系统已有任意地形重建接口。

## 图片以外的六个扩展方向

这些入口可以组合使用，交付仍是有空间结构的真实 3D 场景。选择依据应是用户需要控制什么，而不是输入形式越多越好。

| 方向 | 用户提供什么 | 可形成的产品与产出 | 需要落实的控制 |
| --- | --- | --- | --- |
| 语义绘笔与平面布局 | 水陆分区、道路、关键物体位置和尺度 | 基础画布/plan/不同粗模已实现；继续发展完整场景工具 | 坐标、分区边界、数量已有；连接关系与精细化待建 |
| 现有 3D 资产 | 建筑、角色、道具模型及保留要求 | 围绕已有内容组装世界的工具 | 资源身份、比例、摆放、替换范围、资源预算与许可 |
| 规则与约束 | 岛屿数量、港口靠水、间距、连通性等要求 | 生成多套满足条件的世界方案 | 规则转为实际生成与校验逻辑，失败可解释，不能只依赖提示词 |
| 剧情、任务与事件 | 出生点、探索目标、触发条件、成功条件 | 可试玩的探索关卡或互动故事 | 状态机、交互组件、路线可达与任务验证；剧情文字本身不等于玩法 |
| 镜头与时间线 | 镜头顺序、轨迹、时长、对象动作 | 可重放的虚拟拍摄与实时 3D 演出 | 相机与事件关键帧、时间同步、重放和导出 |
| 地图与真实数据 | 地点、地形高程、建筑或业务数据 | 有真实空间依据的展示与数据场景 | 坐标转换、单位、数据来源与精度；数据缺失处仍要标注和补全 |

单张图片只能提供部分可见外观和投影关系。多视角参考、已有网格、空间布局或地形数据可以补充依据；任何入口都需要场景结构与相应校验。地图输入也不意味着能自动准确复原一个真实地点。

## 资源、规则、玩法与版本各自负责什么

| 层 | 职责 | 当前状态 |
| --- | --- | --- |
| 资源 | 保存几何、材质、纹理、动画及来源，供场景实例引用 | 原版资源、工作台程序几何、新粗模内置几何与参考图；没有任意资源导入和生成管理 |
| 场景方案 | 记录地形分区、对象、尺度、布局与空间关系 | 原工作台配置与独立布局 plan 已有；完整连接/邻接关系和资源引用待建 |
| 规则 | 约束生成与修改，检查数量、位置、连通性和运行预算 | 有限字段、数值/点数、ID 和锁定检查已有；空间生成与可达校验待建 |
| 玩法 | 赋予对象触发、任务和交互行为 | 上游原有游戏系统存在；工作台未接入任务或行为编辑 |
| 版本 | 把已确认方案、生成资源和修改记录一起保存与恢复 | 两类入口的会话历史与本地 JSON、创作 IndexedDB 和旧版快照已有；完整工程版本待建 |

模型可参与解析意图、提出方案、生成资产和实现新组件；运行时执行层负责应用有范围的操作，生成与验证模块负责几何和规则，渲染器负责画面。模型的创作自由不应抹掉这些明确职责。

## Opus 的角色

开发期模型可以协助编写 JavaScript、WGSL 和场景组装代码，运行画面由浏览器 GPU 渲染。这个过程不需要模型拥有直接生图接口；美术资源也可以来自外部资产和程序几何。不能据仓库介绍推断模型独立创作了全部资源或代码。

产品运行时，真实模型可以理解描述并提出有限动作、在资产表中选择对象、解释修改，并结合截图帮助迭代。当前版本没有真实模型调用：原工作台用有限本地解析，新实验由用户手动布局并程序化构建粗模与陆地细节，本地生成说明整理上下文。它们不理解任意描述、不自动识图、不生成任意精细资产，也不冒充 Opus。

## 真实模型的建议接入协议（尚未实现）

建议后端提供 `POST /api/scene/edit` 调用模型供应商。密钥仅保存在后端；当前无此 endpoint，无默认远程请求。调用时发送场景摘要、选择对象、修订号、允许动作和范围，模型输出结构化动作，继续走现有执行器。

下例为建议的后端契约。`sceneSummary` 是模型上下文，执行器仍使用本地完整场景；它不是 Tidewater 原生 API。

此建议协议只适配原生六对象工作台。新实验的布局 plan 是另一份协议；未来模型如何提出区域/路径/资源变更需单独设计，当前可复制生成说明并不等于后端已接通。

```json
{
  "protocolVersion": 1,
  "requestId": "edit-42",
  "sceneRevision": 17,
  "instruction": "把选中的小屋沿世界X轴移动2米，时间改为18点",
  "selectedIds": ["cabin-a"],
  "sceneSummary": {
    "environment": { "timeOfDay": 16.2, "windSpeed": 7, "swell": 0.48, "cloudCover": 0.45 },
    "objects": [{ "id": "cabin-a", "x": -35, "z": -82, "rotation": 0, "scale": 1, "visible": true, "locked": false }]
  },
  "allowedOperations": ["environment", "object", "camera", "preset"],
  "constraints": {
    "positionUnits": "metres",
    "rotationUnits": "degrees",
    "timeOfDay": [0, 24],
    "windSpeed": [0.5, 30],
    "swell": [0, 2],
    "cloudCover": [0, 1],
    "x": [-500, 500],
    "z": [-500, 500],
    "rotation": [-3600, 3600],
    "scale": [0.2, 4],
    "cameraPresets": ["overview", "pier", "boat"],
    "scenePresets": ["harbor", "sunset", "open-water"],
    "unsupported": ["rain", "terrain-generation", "arbitrary-assets"]
  }
}
```

响应只包含动作与说明，不返回可执行代码。相对指令应根据发送时的状态计算绝对值：

```json
{
  "protocolVersion": 1,
  "requestId": "edit-42",
  "sceneRevision": 17,
  "summary": "小屋沿世界X轴移动2米；时间设为18点。",
  "operations": [
    { "type": "object", "id": "cabin-a", "values": { "x": -33 } },
    { "type": "environment", "values": { "timeOfDay": 18 } }
  ],
  "unresolved": []
}
```

接入层需要核对协议、请求 ID 和修订号。场景发生变化时拒绝旧响应或重新请求；不 `eval` 模型输出。执行器继续验证 ID、锁定、字段和范围，整组动作一次应用并加入历史。无法确定目标或存在 `unresolved` 时应解释缺失信息，不把未完成任务显示为成功。

需处理的错误包括 `invalid_schema`、`unknown_object`、`locked_object`、`out_of_range`、`stale_revision`、`model_unavailable`。调用失败可回到明确标注的本地模式；不能把本地规则结果显示为模型结果。

## 后续产品扩展顺序

基础布局、plan、粗模与局部陆地细化已完成本地实验。以下列出后续补全顺序；其余能力尚未实现，也没有验证付费需求。

| 顺序 | 建设重点 | 用户可确认的产物 | 必须补上的能力 |
| --- | --- | --- | --- |
| 1 | 完善语义布局与场景方案确认 | 基础画布、plan 和粗模已有；继续明确关系与范围 | 空间关系、分阶段确认、持久修订；不把粗模等同于精细场景 |
| 2 | 约束与资产管理 | 有可检查规则和明确资源来源的方案 | 空间规则、资产注册/导入、生成资源与版本管理 |
| 3 | 概念图与精细多场景生成 | 可比较外观、可验证空间的不同精细场景 | 模型供应商接口、概念图、精细资源、完整地形重建与依赖更新 |
| 4 | 根据目标用户深化玩法或镜头 | 可试玩关卡，或可重放镜头 | 游戏侧补任务、触发、碰撞/导航；视觉侧补时间轴、同步、编码 |
| 5 | 交付与需求验证 | 可分享、嵌入或再次编辑的作品 | 发布、打包、设备预算、完整版本；与目标用户验证付费价值 |

近期用两个已落地入口和局部细化验证“布局是否能明确表达不同世界、用户能否检查粗模、比较并接受局部补全”，再建设约束/资产与图像、精细 3D 生成。选择、属性、校验和撤销机制已经可用，但它们不会自动获得任意资产或完整地形系统支持。语义画布和本地程序细化不能宣称完成模型自动生成产品。

滨水场景适合作为起点，因为可以复用 Tidewater 的海洋、天空与原生渲染能力。不同世界仍要处理地形、岸浪、植被、村落、碰撞和游戏逻辑的依赖；它不是给现有对象面板再加一个“生成世界”按钮。玩法与镜头应在目标用户明确后选择重点，避免同时建设两套尚未验证的复杂产品。

## 验证与复现
