02 / 生成闭环

每一次反馈，成为下一次输入。

原理示意 · 非官方实测
  1. 01

    当前画面 + 操作

    用户看见已有画面，点击、拖拽，或提出文字要求。

    →
  2. 02

    动作 + 语义条件

    操作位置与轨迹结合上下文；语言描述界定交互的含义。

    →
  3. 03

    公开材料描述鼠标输入作为条件，逐帧自回归生成后续画面。

    →
  4. 04

    看到结果，再操作

    新画面成为接下来交互的状态，形成持续反馈。

依据 Runway 官方介绍 与 论文 v1 整理。该图解释公开机制，不代表内部完整工程架构。

鼠标控制的是条件，生成器负责视觉结果。

传统界面通常先定义对象、属性与事件处理代码。生成式界面可以让模型预测拖动之后的外观；位置、遮挡、光影可能一起变化。看起来合理的结果，仍需要检验其准确性与持续稳定性。

分析推断

“语义”不一定来自每一次事件的即时推理。

论文图 8 中，语言模型维护状态、解释意图并指定行为，世界模型接收操作并生成画面。但公开资料没有说明每个 pointermove 都调用 LLM。具体事件编码与调度需要验证。

展示了什么，还没有证明什么。

公开事实

分析推断

效果好用，仍依赖交互约定。

如果没有选中对象、操作模式或文字指令，同一条轨迹通常存在歧义。因此“可鼠标控制”应进一步拆成对象定位、动作含义、效果稳定性三项来评估。

本地演示中的模式选择，是为了显式呈现这个约定，不代表 Solaris 的官方界面。

待验证边界

演示画面不等于工程数据。

公开材料未证明可编辑 3D、精确尺寸、真实物理求解，也未给出本项目可核验的事件编码、帧率或实测响应延迟。

官方列出文字、可信度、长期一致性，以及无障碍和集成方面的挑战。访问页面时提供早期访问申请。

查看官方限制说明 ↗
拿到真实访问权限后，应该怎么验证？
  1. 同轨迹、不同语义：固定起始画面和拖动轨迹，只改变交互含义，记录结果是否按语义变化。
  2. 精确控制：测试目标选择、细微移动、撤销与重复操作，检查物体、纹理和文字是否漂移。
  3. 连续反馈：记录事件与可见响应的真实时间，长时间操作后检验一致性；保留原始采样条件。
  4. 数据与接入：确认是否能导出结构化状态、3D 或尺寸，确认 API、授权、无障碍和键盘操作支持。
